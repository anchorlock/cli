AI Coding 时，Agent 越多，越需要同一块锚

两下钉同一块锚

船是这次要合进去的代码。锚是那一个机器名：只许 order_no。 没有锚，风会把每条船吹去不同的港。有锚不收紧，锚在水里，船照样漂。 这两下不是同义词：抛锚是写盘前的 MCP，收紧是合并前的 CLI，各对应一条命令。

何时命令（记住这一列）
抛锚Agent 正在写文件SemanticAnchor MCP：bind / verify_usage（吃 constraints.json）
收紧合进主干之前本 CLI：anchor check --contract pin.json --src src --strict --require-hash

anchor constraints --from 不是抛锚，只是从 OpenAPI / pin 投影出抛锚要吃的那份 constraints.json。

抛锚 · SemanticAnchor bind / verify_usage

写盘前：先对照契约再落盘

Agent 要写文件时，编辑器里的 SemanticAnchor 跑 bind / verify_usage。名字不对当场改。这不是 anchor check，本 CLI 只负责准备它要吃的 constraints.json。

收紧 · anchor check

合并前：再扫一遍源码

合进主干前跑 anchor check --contract pin.json --src src --strict --require-hash。抛锚漏了、bind 没绑、有人用手改飘了，卡在这里进不了主干。本机和 CI 挂同一条。

装进仓

QUICK START

安装。一次就够。

需要 Node 18 +。本 CLI 做的是收紧：anchor check 只查字段名。写盘前的抛锚是 SemanticAnchor 的 bind / verify_usage，吃同一份 constraints.json。

01

装进消费仓

在前端 / 客户端 / 测试仓执行 npm i -D @anchorlock/cli。不要拿它去扫同一个 Java 后端仓里的方法和 SQL。全公司钉同一份发版 OpenAPI，不要每个仓各编一份名单。

02

一次 init

只装 Agent 协议，不写字段名单。名单来自 pin 住的 OpenAPI，或一处从代码起草后由人确认。

# 装进你要锁的那个仓 · 只做一次
npm i -D @anchorlock/cli
npx anchor init
去钉 OpenAPI

HOOK INTO YOUR REPO

使用。对照钉死的说明书。

契约必须有仓外权威。编码 Agent 根据需求自己写名单，等于没锁。有 OpenAPI 就 pin；没有就一处起草，人确认一次。

01

Pin 发版 OpenAPI

后端构建导出的 openapi.json 挂在 tag 上。消费仓只提交 contracts/*.pin.json（url + hash），不 clone 后端、不对着 /v3/api-docs。

02

合主干：anchor check --strict

红了改代码对齐说明书，不改 pin。把 FAIL 贴给编码 Agent。函数名（lookupMine()）不算字段。不要用它扫本仓 Java 的 getter 和 SQL 列名。

# 消费仓 · 对照钉死的说明书
npx anchor pin --from dist/openapi.json --url https://…/openapi.json --tag v1.4.0
npx anchor check --contract contracts/order.pin.json --src src --strict --require-hash

不要从工单 / PRD 让 Agent 撰写 constraints.json。没有 OpenAPI 时，用下面的路 B：一处 init --from-code，人确认后再 check。

看怎么分工 →
A

有接口文档：钉住发版说明书

OpenAPI 由后端构建导出（Springdoc / Nest / FastAPI…），不要手写。前端不去 clone 后端仓，也不对着线上最新的 /v3/api-docs 扫。

不要这样

每个仓自己抄一份名单

前端抄出 orderId，后端抄出 order_no。两边 check 都绿，联调还是炸。路 A 不要各 pin 各的。

要这样

消费仓都指向同一份发版说明书

后端打 tag，把说明书挂到发版页。前端只提交 pin：url 填下载链接。check 自己按 url 拉文件。不要拿 check 去扫后端自己的实现代码。

后端仓做什么

  1. 构建导出 openapi.json（框架插件，不手写）
  2. 打 tag，CI 把文件挂到这次 Release
  3. 打开发版页，复制「下载附件」的 https
  4. anchor pin --from dist/openapi.json --url … --tag v1.4.0 -o dist/order.pin.json，把这份 pin 发给前端

前端仓做什么

  1. 把收到的 order.pin.json 放进 contracts/ 并提交（不要手抄 hash，也不要把整份 OpenAPI 提交进来）
  2. 收紧（本机和 CI 同一条）：anchor check --contract contracts/order.pin.json --src src --strict --require-hash
  3. 红了：把 FAIL 贴给编码 Agent，改代码对齐说明书，不要改 pin
  4. 抛锚：先 anchor constraints --from contracts/order.pin.json -o constraints.json，再把 SemanticAnchor 指向它（MCP bind / verify_usage）

pin 只记住说明书在哪。check 才是闸：拿那份说明书对照你仓库里的代码。字段名对不上，这条命令失败，合不进主干。

01

找到那一版说明书

--contract contracts/order.pin.json：读 pin 里的下载地址和指纹，拉下 v1.4.0 的 openapi.json。hash 对不上就停，不拿错文件继续扫。

02

抽出说明书上的字段名

从 OpenAPI 的 schema 属性名得到这份契约认的名字（例如 order_no）。这就是「对」的那一份，前端不另编名单。

03

扫 src/，对不上就红

--src src --strict --require-hash 只看你的业务代码。写了 orderId 而说明书是 order_no → 退出码非 0。把 FAIL 贴给 Agent，改代码，不改 pin。

# ── 后端仓 ── 有 dist/openapi.json。打 tag，算出指纹，把 pin 发给前端
tag="v1.4.0"
git tag "$tag"
git push origin "refs/tags/$tag"
# CI 把 openapi.json 挂到这次发版页，复制「下载附件」的 https
anchor pin --from dist/openapi.json \
  --url "https://git.example.com/group/order-api/-/releases/v1.4.0/downloads/openapi.json" \
  --tag "$tag" -o dist/order.pin.json
# 把 dist/order.pin.json 交给前端（发版附件或拷贝）。前端不要自己再 pin

# 收紧 · 本机和 CI 同一条。红了改代码，把 FAIL 贴给 Agent，不要改 pin
# git add contracts/order.pin.json && git commit
anchor check --contract contracts/order.pin.json --src src --strict --require-hash

# 抛锚前先投影。真正的抛锚是 SemanticAnchor 的 bind / verify_usage（不是这条 CLI）
anchor constraints --from contracts/order.pin.json -o constraints.json

pin 相当于契约的 lockfile：记下「去哪下、指纹是多少」。前端提交它，是为了让本机和 CI 都锁在同一版说明书上，而不是 submodule 后端仓、也不是对着线上 /v3/api-docs 扫。

第二回合：这次需求要加字段

字段范围由后端发版推进，不由你和 Agent 的对话推进。需求说要加「优惠券抵扣」，不等于可以往契约里塞一个 couponAmount——先让后端发版，说明书上有了，前端才认。pin 是整份换，不是往里面加字段。

# 后端发了 v1.5.0 之后，前端换整份。url 里的 tag 跟着换，不用手改
npx anchor repin --from ../order-api/dist/openapi.json --tag v1.5.0 --change PROJ-123

# 看清楚换了什么再提交
git diff contracts/order.pin.json
git add contracts/order.pin.json

# 改业务代码用新字段，跑同一条 check
npx anchor check --contract contracts/order.pin.json --src src --strict --require-hash
  pin   v1.5.0 · change PROJ-123
你想知道的记在哪
现在锁在哪一版pin.json 的 version + hash，每次 check 都打出来
为什么换的这一版pin.json 的 change（需求号）+ 这次 commit
一共换过几次git log contracts/order.pin.json

编码 Agent 不许自己 repin。换版由「后端发布了新版本」触发，不由「check 红了想换绿」触发。红了只能改代码。

B

没有 OpenAPI：从代码起草，人确认一次

没有接口文档，就不要手抄字段清单。命令扫现有源码，把驼峰/下划线收成一份 constraints.json。人只确认，不从空白填起。

谁来扫（只做一次）

  1. anchor init --from-code src 自动写出 constraints.json
  2. 打开文件：删掉函数名、框架词、一次性变量
  3. 判据：留会跨进程传的名字（HTTP JSON key、SQL 列名、MQ payload、存储字段）；删函数名、局部变量、类型名、框架词，以及只在一个文件出现过的名字。拿不准就删
  4. 确认推荐的 snake_case；近义词不会自动合并，要把 id 改成 order_no，并把 orderId / order_sn 写进 aliases
  5. 有枚举再补 values。不要另起一份 txt

其它仓怎么用

  1. 拿到同一份已确认的文件，不要再 init
  2. 收紧：anchor check --contract constraints.json --src src
  3. 抛锚：SA_CONSTRAINTS=./constraints.json，SemanticAnchor 跑 bind / verify_usage
  4. 新字段先改这一份，再写代码。各仓各扫各的，等于没锁
# 只在一处执行。不要前端扫一次、后端再扫一次
anchor init --from-code src
# 自动写出 constraints.json。人只删不该锁的，并把 id 改成要锁的名字
{
  "id": "order_no",
  "aliases": ["orderId", "order_sn", "订单编号", "单号"]
}

anchor check --contract constraints.json --src src
# 上面是收紧。抛锚：SA_CONSTRAINTS=./constraints.json ，再跑 SemanticAnchor bind / verify_usage

连代码都没有、要从零发明字段时，才用 anchor constraints --init 出空白模板。那是例外，不是路 B 的主路径。

CI

挂到合并检查

和跑测试同一位置。失败就不能合。这里挂的是收紧：anchor check。抛锚（bind / verify_usage）发生在编辑器写盘时，不替代这一条。

# 收紧 · 路 A（CI 挂这条，合主干前再拦一次）
npx anchor check --contract contracts/order.pin.json --src src --strict --require-hash
# 收紧 · 路 B
npx anchor check --contract constraints.json --src src

这条 CLI 不做抛锚

抛锚和收紧必须分开记。本包装的是收紧；抛锚是另一个工具，吃同一份契约。

你想做的那一步叫对应命令

SEVERAL AGENTS · NOT PATH C

多个 Agent 同时写：不是第三条路

Cursor、Claude、Copilot 并行，或前端 / 后端 / 测试各开一个 Agent，仍走路 A（没有说明书则路 B）。协作增加的是写代码的人，不是契约的份数。共享 contracts/order.pin.json，CI 只认同一条 check。

人 / 后端 Agent

  1. 人：第一次 pin；后端发新 tag 后 repin --change <需求号>
  2. 后端 Agent：实现接口、导出 OpenAPI、打 tag
  3. 不要在消费仓里扫后端自己的 Java，也不要手写名单当权威

前端 / 测试 Agent

  1. 用说明书上的名字写代码。红了把整段 FAIL 贴给写飘的那个 Agent
  2. 不许 repin、改 pin、按这次对话另编名单
  3. 跨仓顺序：后端发版 → 人 repin → 消费仓 Agent 才用新字段。测试仓和前端仓 pin 同一个 tag
